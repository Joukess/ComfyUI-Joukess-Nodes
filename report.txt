Ці два числа вимірюють різне, тому вони й не збігаються.

**Що показує бейдж 0.001s.** Це час, який ComfyUI витратив саме на виконання функції ноди Step Indices. Нічого іншого в нього не входить.

**Що показує ваш таймер (0.01 s).** Це весь проміжок між двома моментами часу:
1. Нода Start зберігає `perf_counter()` у змінну, а потім ще **записує JSON-файл на диск** (`_save_state`). Цей запис уже входить у відлік, бо мітка часу взята до нього.
2. Між нодами працює виконавець ComfyUI: перевірка кешу і `IS_CHANGED` (у вас `nan`, тож завжди перевиконання), підготовка вхідних даних, відправлення подій у фронтенд через websocket.
3. Виконується Step Indices (0.001 s).
4. Нода End **читає JSON з диска** (`_load_state`) і лише після цього викликає `perf_counter()`. Тобто читання файлу теж потрапляє у вимір.

Разом виходить кілька мілісекунд на файлові операції та ще кілька на службові витрати ComfyUI. Формат `.2f` показує 0.01, тобто реальне значення десь між 5 і 15 мс. На Windows відкриття й запис маленького файлу легко займає 2–5 мс, особливо з антивірусом.

Бейдж 0.019s на самій нодi End теж це підтверджує: більшу частину часу забирає саме робота з файлом, а не логіка.

**Як зменшити похибку.** Для `PromptTimerCurrent` файл не потрібен, бо старт і кінець відбуваються в одному процесі. Тримайте старт у змінній модуля, у Start беріть мітку часу останньою дією, а в End першою:

```python
_current_start = None

class PromptTimerCurrent:
    ...
    def run(self, mode, any=None):
        global _current_start

        if mode == "Start":
            _current_start = time.perf_counter()  # остання дія перед return
            return ("0.00", any)

        now = time.perf_counter()  # перша дія в End
        if _current_start is None:
            return ("0.00", any)

        elapsed = max(0.0, now - _current_start)
        _current_start = None
        return (f"{elapsed:.2f}", any)
```

Тоді у вимір потраплять тільки проміжні ноди й накладні витрати виконавця, а це, найімовірніше, дасть 0.00–0.01. Повністю збіг із бейджем ноди неможливий: таймер завжди вимірює «стіну» між нодами, а не роботу окремої ноди. На реальних workflow із секундами чи хвилинами генерації ця різниця в кілька мілісекунд не має значення.

Зверніть увагу, що `PromptTimerAverage` теж пише й читає файл, і там ця сама похибка. Для середнього часу тривалих прогонів вона мізерна, але файл можна лишити тільки для збереження підсумкової статистики, а `start_time` теж тримати в пам'яті.
